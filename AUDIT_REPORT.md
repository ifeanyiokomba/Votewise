# VoteWise Independent Security & Correctness Audit

**Auditor:** Independent security review (read-only)
**Scope:** Full codebase at `/home/z/my-project` (multi-tenant election-as-a-service platform)
**Date:** August 2026
**Methodology:** Static source review, dependency audit, schema review, configuration review, mechanical tooling pass (tsc, eslint, prisma validate, bun audit).

> ⚠️ **The audit was performed on a live filesystem that contained a populated `.env` file with what appear to be real production secrets (DATABASE_URL with Neon credentials, SESSION_SECRET, ENCRYPTION_KEY).** This is itself the #1 finding (F-01). The reviewer did not modify any code or exfiltrate any data, but any party with read access to this filesystem — including past CI runs, backups, or container images — has had unrestricted access to these secrets.

---

## 1. Executive Summary

VoteWise is a substantial, ambitious multi-tenant election platform: ~330 TypeScript/React source files, a 672-line Prisma schema covering 19 models, three Socket.io mini-services, Paystack payment integration, OTP verification across three channels, AES-256-GCM credential encryption, an audit log, and a real-time monitoring stack. The architecture is generally well-intentioned and shows clear evidence of iterative hardening (e.g. the explicit "Finding #4" / "Finding #5" / "Finding #14" annotations show prior security review work).

**However, in its current state the codebase is not safe to operate as a real election system.** The audit identified **39 distinct findings**, of which **7 are Critical** and **12 are High** severity. The most serious classes of defect are:

1. **Secret hygiene collapse.** Live secrets are sitting on disk in `.env`; the platform admin password is hardcoded as a fallback in `prisma/seed.ts`; ESLint and TypeScript error-checking are both effectively disabled, so silent regressions will ship to production.

2. **Tenant isolation holes.** Multiple admin endpoints mutate child records by raw ID without re-scoping to the caller's `organizationId` — toggling voter eligibility, deleting announcements, resolving security events, updating support tickets, and marking notifications read can all be performed cross-tenant.

3. **Election-integrity bypasses.** Candidates and positions can be edited or deleted while an election is LIVE; the scheduler service writes status changes directly without consulting the state machine; the public observer endpoint is completely unauthenticated and leaks turnout/timeline data for any election by ID; a double-voting race window exists because `VotingSession` has no unique constraint on `(voterId, electionId)`.

4. **Commercial bypass.** `POST /api/admin/subscription/upgrade` upgrades an org to PROFESSIONAL tier (₦150,000) **instantly and for free** with no payment verification — the code comment even says "Simulated verified payment (server-side only). In production a webhook confirms" but no such webhook exists for subscriptions.

5. **Mini-service trust boundary broken.** The monitor Socket.io service and support-chat Socket.io service both bind to `0.0.0.0`, accept connections from `cors: { origin: "*" }`, and have **zero authentication** on any event. Anyone on the internet can subscribe to live vote counts for any election, or impersonate any voter or admin in support chat. The monitor service is also hardcoded to a SQLite path that does not match the production PostgreSQL database — meaning it is either dead code in production or a deployment-time landmine.

6. **No tests, no CI, no migrations.** The `prisma/migrations/` directory does not exist; schema changes are applied via `prisma db push --accept-data-loss`. There is no `.github/` directory, no test files anywhere in the repo, and the only quality gate (`bunx eslint .`) is rendered meaningless by an `eslint.config.mjs` that turns off every meaningful rule.

**Recommendation:** Do not run a real election on this codebase until at least the Critical findings (F-01 through F-07) are remediated. The High findings should be addressed before any production deployment that affects more than a trivial number of voters.

## 6. Closing Notes

This audit was conducted read-only. No code was modified, no data was exfiltrated, no secrets were tested against live systems. The findings above represent the reviewer's best-effort assessment based on static analysis of the codebase as it existed at the time of review.

The VoteWise codebase shows clear evidence of thoughtful design — the ballot-secrecy model (anonymousToken with sessionId removed), the Paystack webhook's defense-in-depth (HMAC + API verify + amount check), the AES-256-GCM with separated keys, and the explicit "Finding #N" annotations all indicate prior security work. The findings here should be read as "the next iteration of hardening," not as a condemnation of the existing effort.

That said, the gap between the codebase's current state and "safe to run a real election" is substantial. The Critical findings (F-01 through F-07) represent existential risks: anyone with filesystem access has the production keys; anyone with internet access can subscribe to live election monitoring; any org admin can upgrade their tier for free; the type checker is disabled so silent regressions ship daily. These must be addressed before any further elections are conducted on this platform.

The reviewer is available for clarification on any finding and recommends a follow-up audit after the Must-fix items are remediated.
